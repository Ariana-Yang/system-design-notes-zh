# 第 11 章：设计一个新闻信息流系统

## 引言
**新闻信息流系统**会显示来自用户关系网络的、不断更新的帖子列表（状态更新、照片、视频和链接）。示例包括 Facebook 的新闻信息流、Instagram 的信息流以及 Twitter 的时间线。本章探讨可扩展新闻信息流系统的设计。

---

## 步骤 1：理解问题

### 需求
1. **平台：** 系统同时支持 Web 和移动应用。
2. **功能：**
   - 用户可以发布帖子。
   - 用户可以在自己的新闻信息流中查看朋友的帖子。
3. **排序：** 为简单起见，信息流按**逆时间顺序**排序。
4. **规模：**
   - 用户最多可以拥有 5,000 个朋友。
   - 10 million 日活跃用户（DAU）。
   - 信息流可能包含文本、图片和视频。

---

## 步骤 2：高层设计

### 概览
设计包含两个主要流程：
1. **信息流发布：** 用户发布帖子，帖子会写入数据库并传播到其朋友的信息流。
2. **新闻信息流构建：** 用户通过聚合朋友的帖子，按逆时间顺序获取自己的新闻信息流。

---

### 新闻信息流 API
1. **信息流发布 API：**
   - **端点：** `POST /v1/me/feed`
   - **参数：** `content`（帖子文本）和 `auth_token`（身份验证）。

2. **新闻信息流获取 API：**
   - **端点：** `GET /v1/me/feed`
   - **参数：** `auth_token`（身份验证）。

1. **用户交互：** 用户通过信息流发布 API 发布帖子。
2. **负载均衡器：** 将流量分发到 Web 服务器。
3. **Web 服务器：** 对请求进行身份验证并将请求转发到服务。
4. **帖子服务：** 将帖子存储在数据库和缓存中。
5. **扇出服务：** 将帖子传播到缓存中的朋友新闻信息流。
6. **通知服务：** 向朋友发送通知。

1. **用户交互：** 用户通过获取 API 请求自己的新闻信息流。

3. **Web 服务器：** 将请求转发到新闻信息流服务。
4. **新闻信息流服务：** 从新闻信息流缓存中获取帖子 ID，并从数据库或缓存中获取完整的帖子详情。

## 步骤 3：深入设计

### 信息流发布深入设计
1. **Web 服务器：**
   - 使用 `auth_token` 对用户进行身份验证。
   - 强制执行速率限制以防止垃圾信息。

2. **扇出服务：**
   - **写时扇出：** 在写入时将帖子推送到朋友的信息流。
     - **优点：** 实时更新，信息流获取速度快。
     - **缺点：** 对拥有大量朋友的用户来说资源消耗大。
   - **读时扇出：** 在读取时拉取帖子。
     - **优点：** 对不活跃用户来说效率高。
     - **缺点：** 信息流获取速度较慢。
   - **混合方式：** 对大多数用户使用推送模型，对连接数较多的用户（例如名人）使用拉取模型。

        <img src="./images/feed-publishing-deep-dive.png" alt="信息流发布深入设计" width="500">

    **扇出服务**的工作流程如下：

    1. **获取朋友 ID：** 从图数据库中获取朋友列表。
    2. **从缓存中过滤朋友：** 访问缓存中的用户设置，以排除某些朋友（例如被静音的朋友或具有选择性分享偏好的朋友）。
    3. **发送到消息队列：** 将过滤后的朋友列表和新帖子 ID 一起发送到消息队列进行处理。
    4. **扇出工作线程：** 工作线程从消息队列中获取数据并更新新闻信息流缓存。缓存存储 `<post_id, user_id>` 映射，而不是完整的用户和帖子对象，以节省内存。
    5. **存储到新闻信息流缓存：** 将新的帖子 ID 追加到朋友的新闻信息流缓存中。可配置的限制确保只存储最近的帖子，因为大多数用户关注最新内容，从而使缓存内存消耗保持在可管理范围内。

## 新闻信息流获取深入设计

### 缓存架构
缓存分为五层：
1. **新闻信息流缓存：** 存储帖子 ID，以便快速获取。
2. **内容缓存：** 存储帖子详情（热门帖子存放在热缓存中）。
3. **社交图谱缓存：** 存储用户关系数据。
4. **操作缓存：** 跟踪用户操作（点赞、回复、分享）。
5. **计数器缓存：** 维护点赞、回复、关注者等数量。

## 关键优化

### 扩展
1. **数据库扩展：**
   - 水平扩展和分片。
   - 对高流量查询使用只读副本。
2. **无状态 Web 层：** 保持 Web 服务器无状态，以实现水平扩展。

### 缓存
1. 将频繁访问的数据存储在内存中。
2. 使用缓存层来降低延迟和数据库负载。

### 可靠性
1. **一致性哈希：** 在服务器之间均匀分配请求。
2. **消息队列：** 解耦系统组件并缓冲流量。

### 监控
1. 跟踪 QPS（每秒查询数）和延迟等关键指标。
2. 监控缓存命中率并相应地调整配置。

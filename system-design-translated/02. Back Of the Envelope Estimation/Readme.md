# 第 2 章：粗略估算

## 引言
粗略估算是系统设计面试中的一项关键技能。它涉及进行快速、粗略的计算，以评估系统容量或性能。根据 Google 高级研究员 Jeff Dean 的说法，这些估算通过思想实验和常见的性能基准，帮助评估设计是否满足要求。

本章介绍可用于提高可扩展性和估算能力的关键概念、方法和示例。

### 每个程序员都应该知道的延迟数字
延迟数字表示计算系统中各种操作所花费的时间。这些数字可以帮助了解相对性能：

| 操作                     | 延迟（2020）    |
|--------------------------|----------------|
| L1 缓存访问              | 0.5 ns         |
| L2 缓存访问              | 7 ns           |
| 主内存访问               | 100 ns         |
| SSD 随机读取             | 150 µs         |
| HDD 随机寻道             | 10 ms          |
| 数据中心往返             | 500 µs        |
| 跨区域数据中心           | 150 ms         |

**关键洞察：**
- 内存很快，磁盘很慢。
- 尽可能避免磁盘寻道。
- 在通过互联网传输数据之前进行压缩，以节省带宽。


---

### 可用性数字
高可用性（HA）确保停机时间最少。可用性用**几个九**表示：
- **99%（两个九）：**每年约 3.65 天的停机时间
- **99.9%（三个九）：**每年约 8.8 小时的停机时间
- **99.99%（四个九）：**每年约 52 分钟的停机时间
- **99.999%（五个九）：**每年约 5.3 分钟的停机时间
- **99.9999%（六个九）：**每年约 31.56 秒的停机时间


Amazon、Google 和 Microsoft 等云提供商的目标是达到 **99.9% 或更高**的 SLAs（服务级别协议）。

## 第 2 节：估算示例 - Twitter QPS 和存储需求

### 假设
- **每月活跃用户（MAU）300 百万。**
- **每日活跃用户（DAU）占 50%。**
- **平均每个用户每天发布的推文数：**2。
- **10% 的推文包含媒体。**
- **数据保留时间：**5 年。

### 估算
1. **每秒查询数（QPS）：**
   - DAU = \( 300M x 50\% = 150M \)
   - Tweets QPS = \( 150M x 2 tweets / 24 hour / 3600 seconds = ~3500 )
   - Peak QPS = \( 2 x 3500 = ~7000 \)

2. **媒体存储：**
   - **推文大小组成：**
     - `tweet_id`：64 bytes
     - `text`：140 bytes
     - `media`：1 MB
   - **每日媒体存储：**\( 150M x 2 x 10\% x 1MB = 30TB per day \)
   - **5 年存储：**\( 30TB x 365 x 5 = ~55PB \)

## 第 3 节：有效估算的技巧

### 1. 四舍五入和近似
精确度并不关键；重点是过程。使用整数量级简化复杂计算。例如：
- \( 99987 / 9.1 \) 可以近似为 \( 100,000 / 10 = 10,000 \)。

### 2. 写下假设
清楚记录假设，以便将来参考。

### 3. 标注单位
通过标注单位避免歧义（例如使用 `5 MB` 而不是 `5`）。

### 4. 常见估算场景
- **QPS（每秒查询数）：**衡量流量强度。
- **峰值 QPS：**考虑流量峰值。
- **存储需求：**估算总数据需求。
- **缓存需求：**评估缓存所需的内存。
- **服务器数量：**根据工作负载计算所需的硬件。

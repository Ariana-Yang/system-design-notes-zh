# 第 26 章：支付系统

## 简介
本章将设计一个**支付系统**，它支撑着现代所有的**电子商务**。

**支付系统**用于结算金融交易，转移货币价值。

---

## 步骤 1：理解问题并确定设计范围
 * C：我们正在构建什么类型的支付系统？
 * I：一个电子商务系统的支付后端，类似于 Amazon.com。它处理所有与资金流动有关的事情。
 * C：支持哪些支付选项——信用卡、PayPal、银行卡等？
 * I：现实中系统应支持所有这些选项。为了面试，我们可以使用信用卡支付。
 * C：我们自己处理信用卡吗？
 * I：不，我们使用 Stripe、Braintree、Square 等第三方提供商。
 * C：我们在系统中存储信用卡数据吗？
 * I：出于合规原因，我们不会直接在系统中存储信用卡数据，而是依赖第三方支付处理商。
 * C：应用是全球化的吗？我们是否需要支持不同的货币和国际支付？
 * I：应用是全球化的，但为了面试，我们假设只使用一种货币。
 * C：我们每天支持多少笔支付交易？
 * I：1mil 笔交易/天。
 * C：我们是否需要支持支付给付款方的支付出账流程，例如每月向付款方出账？
 * I：是的，我们需要支持该流程
 * C：还有什么需要我注意的吗？
 * I：我们需要支持对账，以修复与内部和外部系统通信时出现的任何不一致。

### **功能需求**
 * 收款流程 - 支付系统代表商户从客户处收款
 * 付款流程 - 支付系统向世界各地的卖家付款

### **非功能需求**
 * 可靠性和容错性。失败的支付需要谨慎处理
 * 需要建立内部和外部系统之间的对账机制。

### **粗略估算**
系统每天需要处理 1mil 笔交易，即每秒 10 笔交易。

对于任何数据库系统而言，这都不是高吞吐量，因此这不是本次面试的重点。

### **收款流程**
下面是收款流程的高层概览：

<div style="margin-left:3rem">
    <img src="./images/payin-flow-high-level.png" alt="收款流程高层图" width="500" />
</div>

 * 支付服务 - 接收支付事件并协调支付流程。它通常还会使用第三方提供商执行风险检查，以检查 AML 违规或犯罪活动。
 * 支付执行器 - 通过支付服务提供商（PSP）执行单个支付订单。支付事件可能包含多个支付订单。
 * 支付服务提供商（PSP）- 将资金从一个账户转移到另一个账户，例如从买方的信用卡账户转移到电子商务网站的银行账户。
 * 卡组织 - 处理信用卡操作的组织，例如 Visa、MasterCard 等。
 * 账本 - 保存所有支付交易的财务记录。
 * 钱包 - 保存所有商户的账户余额。

下面是一个收款流程示例：
 * 用户点击“下单”，一条支付事件被发送到支付服务
 * 支付服务将事件存储在其数据库中
 * 支付服务为该支付事件中的所有支付订单调用支付执行器
 * 支付执行器将支付订单存储在其数据库中
 * 支付执行器调用外部 PSP 处理信用卡支付
 * 支付执行器处理完支付后，支付服务更新钱包，以记录卖家拥有的金额
 * 钱包服务将更新后的余额信息存储在其数据库中
 * 支付服务调用账本，记录所有资金移动

### **支付服务的 API**
```
POST /v1/payments
{
  "buyer_info": {...},
  "checkout_id": "some_id",
  "credit_card_info": {...},
  "payment_orders": [{...}, {...}, {...}]
}
```

示例 `payment_order`：
```
{
  "seller_account": "SELLER_IBAN",
  "amount": "3.15",
  "currency": "USD",
  "payment_order_id": "globally_unique_payment_id"
}
```

注意事项：
 * `payment_order_id` 会转发给 PSP 以去重支付，即它是幂等键。
 * amount 字段是 `string`，因为 `double` 不适合表示货币值。

```
GET /v1/payments/{:id}
```

此端点根据 `payment_order_id` 返回单笔支付的执行状态。

### **支付服务数据模型**
我们需要维护两张表——`payment_events` 和 `payment_orders`。

对于支付而言，性能通常不是重要因素。但强一致性很重要。

选择数据库时还要考虑：
 * 有充足的 DBA 人才可雇用来管理 databaseS
 * 有经过验证的使用记录，其他大型金融机构曾使用过该数据库
 * 支持工具的丰富程度
 * 相比 NoSQL/NewSQL 采用传统 SQL，以获得 ACID 保证

以下是 `payment_events` 表包含的内容：
 * `checkout_id` - 字符串，主键
 * `buyer_info` - 字符串（个人备注 - 也许使用另一张表的外键更合适）
 * `seller_info` - 字符串（个人备注 - 同上）
 * `credit_card_info` - 取决于卡提供商
 * `is_payment_done` - 布尔值

以下是 `payment_orders` 表包含的内容：
 * `payment_order_id` - 字符串，主键
 * `buyer_account` - 字符串
 * `amount` - 字符串
 * `currency` - 字符串
 * `checkout_id` - 字符串，外键
 * `payment_order_status` - 枚举（`NOT_STARTED`、`EXECUTING`、`SUCCESS`、`FAILED`）
 * `ledger_updated` - 布尔值
 * `wallet_updated` - 布尔值

注意事项：
 * 有许多支付订单与给定的支付事件关联
 * 收款流程不需要 `seller_info`。只有付款流程需要它
 * 当调用相应服务记录支付结果时，会更新 `ledger_updated` 和 `wallet_updated`
 * 支付状态转换由后台作业管理，该作业检查进行中支付的更新，如果支付未在合理时间内处理，则触发警报

### **复式记账账本系统**
复式记账机制是任何支付系统的关键。它通过始终对两个账户应用货币操作来跟踪资金移动：一个账户的余额增加（贷记），另一个账户的余额减少（借记）：

| 账户   | 借记 | 贷记 |
|---------|-------|--------|
| 买方   | $1    |        |
| 卖方   |       | $1     |

所有交易分录的总和始终为零。该机制提供了系统内所有资金移动的端到端可追溯性。

## 步骤 3：深入设计
本节重点是让系统更快、更强健且更安全。

### **PSP 集成**
如果我们的系统可以直接连接银行或卡组织，则无需 PSP 即可完成支付。
这类连接非常少见且不常见，通常只有能够证明投资合理的大型公司才会采用。

如果采用传统路线，PSP 可以通过两种方式之一进行集成：
 * 通过 API，如果我们的支付系统可以收集支付信息
 * 通过托管支付页面，以避免处理支付信息法规

下面是托管支付页面的工作流程：

<div style="margin-left:3rem">
    <img src="./images/hosted-payment-page-workflow.png" alt="托管支付页面工作流程" width="500" />
</div>

 * 用户在浏览器中点击“结账”按钮
 * 客户端使用支付订单信息调用支付服务
 * 收到支付订单信息后，支付服务向 PSP 发送支付注册请求。
 * PSP 接收支付信息，例如货币、金额、有效期等，以及用于幂等性的 UUID。通常使用支付订单的 UUID。
 * PSP 返回一个唯一标识支付注册的令牌。令牌存储在支付服务数据库中。
 * 令牌存储后，系统向用户提供 PSP 托管的支付页面。该页面使用令牌以及成功/失败重定向 URL 进行初始化。 
 * 用户在 PSP 页面填写支付详细信息，PSP 处理支付并返回支付状态
 * 用户现在被重定向回 redirectURL。重定向 URL 示例 - `https://your-company.com/?tokenID=JIOUIQ123NSF&payResult=X324FSa`
 * PSP 异步通过 webhook 调用我们的支付服务，以通知后端支付结果
 * 支付服务根据收到的 webhook 记录支付结果

### **对账**
上一节解释了支付的正常路径。异常路径通过后台对账流程检测并进行对账。

每天晚上，PSP 会发送结算文件，我们的系统使用它将外部系统的状态与内部系统的状态进行比较。

<div style="margin-left:3rem">
    <img src="./images/settlement-report.png" alt="结算报告" width="500" />
</div>

此流程也可用于检测例如账本和钱包服务之间的内部不一致。

不匹配由财务团队手动处理。不匹配的处理方式包括：
 * 可分类，因此这是已知的不匹配，可以使用标准流程进行调整
 * 可分类，但无法自动化。由财务团队手动调整
 * 不可分类。由财务团队手动调查并调整

### **处理支付处理延迟**
有些情况下，支付可能需要数小时才能完成，尽管通常只需要几秒。

这可能是由于：
 * 支付被标记为高风险，需要有人进行人工审核
 * 信用卡需要额外保护，例如 3D Secure Authentication，需要持卡人提供额外详细信息才能完成

这些情况的处理方式是：
 * 等待 PSP 在支付完成时向我们发送 webhook；如果 PSP 不提供 webhook，则轮询其 API
 * 向用户显示“待处理”状态，并为他们提供一个可以查看支付更新的页面。支付完成后，我们也可以向他们发送电子邮件

### **内部服务之间的通信**
服务相互通信时使用的通信模式有两种——同步和异步。

同步通信（即 HTTP）适用于小规模系统，但随着规模扩大而受到影响：
 * 性能低——随着调用链中涉及更多服务，请求-响应周期变长
 * 故障隔离能力差——如果 PSP 或任何其他服务发生故障，用户将收不到响应
 * 紧耦合——发送方需要知道接收方
 * 难以扩展——由于没有缓冲区，不容易支持流量突然增加

异步通信可以分为两类。

单个接收者 - 多个接收者订阅同一主题，但消息只处理一次：

<div style="margin-left:3rem">
    <img src="./images/single-receiver.png" alt="单个接收者" width="500" />
</div>

多个接收者 - 多个接收者订阅同一主题，但消息会转发给所有接收者：

<div style="margin-left:3rem">
    <img src="./images/multiple-receiver.png" alt="多个接收者" width="500" />
</div>

后一种模型很适合我们的支付系统，因为一次支付可以触发多个副作用，这些副作用由不同的服务处理。

简而言之，同步通信更简单，但不允许服务自治。 
异步通信以简单性和一致性换取可扩展性和韧性。

### **处理失败的支付**
每个支付系统都需要处理失败的支付。以下是我们用来实现这一目标的一些机制：
 * 跟踪支付状态——每当支付失败时，我们可以根据支付状态确定是重试还是退款。
 * 重试队列——需要重试的支付会发布到重试队列
 * 死信队列——最终失败的支付会被推送到死信队列，在那里可以调试和检查失败的支付。

### **恰好一次投递**
我们需要确保支付被恰好处理一次，以避免向客户重复扣费。

如果一个操作同时至少执行一次且至多执行一次，那么该操作就是恰好执行一次。

为了实现至少一次的保证，我们将使用重试机制：

<div style="margin-left:3rem">
    <img src="./images/retry-mechanism.png" alt="重试机制" width="500" />
</div>

以下是一些决定重试间隔的常见策略：
 * 立即重试——客户端在失败后立即发送另一个请求
 * 固定间隔——在重试支付前等待固定时长
 * 增量间隔——逐步增加每次重试之间的重试间隔
 * 指数退避——将后续重试之间的重试间隔加倍
 * 取消——客户端取消请求。当错误是终止性的或达到重试阈值时会发生这种情况

经验法则是默认采用指数退避重试策略。一个好的做法是让服务器使用 `Retry-After` 标头指定重试间隔。

重试存在一个问题：服务器可能会处理支付两次：
 * 客户端点击“支付按钮”两次，因此被扣费两次
 * PSP 已成功处理支付，但下游服务（账本、钱包）没有处理。重试会导致 PSP 再次处理该支付

要解决重复支付问题，我们需要使用幂等机制——一种操作被应用多次时只处理一次的属性。

从 API 角度看，客户端可以进行多次调用并产生相同结果。 
幂等性通过请求中的特殊标头（例如 `idempotency-key`）进行管理，该标头通常是 UUID。

<div style="margin-left:3rem">
    <img src="./images/idempotency-example.png" alt="幂等性示例" width="500" />
</div>

可以使用数据库添加唯一键约束的机制实现幂等性：
 * 服务器尝试在数据库中插入新行
 * 由于违反唯一键约束，插入失败
 * 服务器检测到该错误，转而将现有对象返回给客户端

幂等性也应用在 PSP 侧，使用此前讨论过的 nonce。PSP 会确保不会两次处理具有相同 nonce 的支付。

### **一致性**
在支付生命周期中，会调用多个有状态服务——PSP、账本、钱包、支付服务。

任意两个服务之间的通信都可能失败。 
我们可以通过实现恰好一次处理和对账，确保所有服务之间最终达到数据一致。

如果使用复制，就必须处理复制延迟，这可能导致用户在主数据库和副本数据库之间观察到不一致的数据。

为缓解这一点，我们可以让所有读写都来自主数据库，并且仅使用副本进行冗余和故障转移。
或者，我们可以使用 Paxos 或 Raft 等共识算法，确保副本始终保持同步。
我们还可以使用基于共识的分布式数据库，例如 YugabyteDB 或 CockroachDB。

### **支付安全**
以下是一些可以用来确保支付安全的机制：
 * 请求/响应窃听——我们可以使用 HTTPS 保护所有通信
 * 数据篡改——强制加密并进行完整性监控
 * 中间人攻击——使用 SSL \w 证书固定
 * 数据丢失——在多个区域复制数据并创建数据快照
 * DDoS 攻击——实施速率限制和防火墙
 * 卡片盗窃——使用令牌，而不是在系统中存储真实卡片信息
 * PCI 合规——针对处理品牌信用卡的组织制定的安全标准
 * 欺诈——地址验证、卡片验证值（CVV）、用户行为分析等
